## 1. Frame-4801 instruction count: 2271 vs 2224 - UNREPRODUCED, artifact of an intermediate build

Measurements today on the identical input `private/review/authentic-krell-capture4802/frame-4801-slot-1-owned-before`
(creatures.bin sha256 prefix `52e97a9d4de85a1f`, also identical to `authentic-krell-183/frame-4801-slot-1-owned-before`):

- `owned-mule-captured-width-review.py --before <fixture> --frame 4801 --slot 1` -> status `source_prepared`, **2224 instructions**, 0 draws;
- same fixture with `--expected <port output>` -> status `mismatch` on that stale dir, **2224 instructions**, 0 draws, `compared_bytes 427369`;
- `scripts/root_family_check.py` runs F1-check-20261017T0935 and T0945 -> **2224 instructions**, 0 draws, 0 diffs.

So 2224 is stable and reproduces the pinned receipt value; the worker's 2271 figure was **not reproduced**.
Most likely source: attempt11's *intermediate* build state during its line-ending-churn episode. Its leftover
regression output `private/review/gw5922-attempt11-reg-4801` (creatures.bin prefix `6c71bde4...`) disagrees with the
interpreter's output for the same input by **14 bytes in record 1** (offsets 218, 220, 221 and 232-240). That is
evidence of a broken intermediate binary, not of the committed tree: after the worker rebuilt byte-exact and after the
family checkpoint, the same case is 0-diff.

Conclusion: **recovered tooling/build problem, not a gameplay divergence**. The committed tree is byte-exact at 4801.

## 2. Provisional: the 6BA47 food-guard path (matrix row F1-R13) - RESOLVED 2026-10-17 (F13/F14)

The measured trace for the 5924 owned command dispatch enters `0x6ba3b..0x6ba4c` and leaves at `0x6bd2b` after
6 instructions, so the source runs a guard that does not enter its scan loop. The port currently skips its own
neighborhood scan for that domain instead of reconstructing the guard. It is **state-invisible** for the measured
fixture (0-diff, 2 draws), but it is a path-fidelity gap and is carried as `provisional`, not as proved.

**RESOLVED (F13/F14, 2026-10-17):** the provisional food-guard reading was wrong. The validated image
`private/ghidra/validated/memory-.object1.bin` (load base 0x10000) pins `0x6ba47..0x6ba4c` as the kind
dispatch (`cmp` kind 1 < 2 -> `0x6bd2b`, and `0x6bd2d` `jz 0x6ba8a` taken), which is exactly the observed
"enters 0x6ba3b..0x6ba4c, leaves at 0x6bd2b" - it was never a food-guard skip; it is the kind-dispatch path
into the hostile kind-1 scoring arm (`0x6ba8a..0x6baf3`). Evidence: F13 checkpoint
`research/integration/f13-5966-neighborhood-answer-checkpoint-20261017.json`; the F14 port arm
(`owned_mule_single_hostile` hostile kind-1 classification + widened
`mule_owned_hostile_acquisition::plan_acquisition`) matches the owned oracle byte-for-byte on the 5966
record (zero diffs, 4 draws, trace `9c48d067bdd04c5d807ca4c4ce3140d3`).
