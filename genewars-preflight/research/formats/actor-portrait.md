# Selected actor portrait draw

The selected-actor details path calls the actor's virtual draw slot from two panel render methods. At `0x266EC` in function `0x265F0` and `0x2800D` in `0x27F20`, the actor pointer is in EAX, its vtable is in ECX, and the caller has loaded EBX=`0x2A`, EDX=`0x19` before `CALL [ECX+0x18]`. The actor vtable entry at `0x1121AC` resolves to `0x57050`.

`0x57050` sign-extends DX and BX, sets global `0x115B58` around the actor's virtual `+0x24` draw, then clears that global. In `0x57070`, DX supplies component X and BX supplies component Y. The selected panel portrait origin is therefore **(25, 42)** on the full 640×480 display. With `0x115B58` set, the draw path omits the world shadow call and does not subtract virtual-height/64 from the supplied Y. Its ordinary visibility, shade, and color path remains active.

Selection itself is connected: `0x2A450` resolves the chosen player-list entry to an actor record and passes it through `0x258E0` to the selected-panel object. The UI callsites above then draw the actor before the adjacent detail labels/statistics. The renderer helper takes the selected slot explicitly and adds this portrait over the already rendered indexed frame; it does not infer selection state or reconstruct the rest of the panel.

`actor_scene.rs` has an actual-resource test that compares the full portrait result against an independent component pixel walk, verifies the change stays in the left 128-pixel panel, and checks a synthetic clipped placement. The focused test passes. Exact source pins and the test command are recorded in [`actor-portrait-evidence.json`](../ghidra/actor-portrait-evidence.json).

## Adjacent details evidence

The top string in the `0x265F0` panel path uses the executable format string at `0x10D687`, whose bytes are `%s\n%s`. Its first argument is the pointer at actor-object offset `0xC0`; its second is loaded from `0x116090 + sign_extend(blueprint[0x16])*4`. The initializer binds `actor+0xC0` to a typed `BlueprintRecordHandle`, which resolves to `PlayerState.blueprint(index)`, a 36-byte record. Its generated name is NUL-terminated in bytes `[0,20)`. The zeroed bytes in the initialized executable image are only the text pointer table's initial state. Startup function `0x1D770` fills the larger pointer array at `0x115E90 + 4*i` from the 604 parsed text strings (loop `0x1DA60`–`0x1DA7B`). Consequently `0x116090` is entry 128, and category values 0–3 resolve entries 128–131. These are the four category strings used by this format path. The renderer resolves them from the parsed text table without embedding their contents. The selector's wider domain is not established here, so a safe adapter rejects values outside the four admitted entries.

The `0xC0` value is not a string in the native actor byte array; it is the typed handle into the owning player's blueprint table. The panel's `0x1F490` call sets a clipped text viewport at `(84,382)` with width 78 and height 21. The subsequent `0x1F750` call uses local cursor `(0,0)` and font context `0x187054`; the name starts at `(84,382)`. Control handler `0x1FE70` dispatches newline byte `0x0A` to `0x1FEEC`, which advances by the height byte at the context's first glyph record and restores the saved baseline. With the pinned FONT0 pair this space-glyph height is 8, so the category line begins at `(84,390)`. The two-line helper renders inside the exact 78×21 viewport and leaves outside pixels unchanged. `research/ghidra/actor-panel-text-evidence.json` records the source pins and exact bounds.

The selected text context does not draw FONT0 literal bytes as plain palette indices. `0x265F0` sets its low context flags to `0x07`; `0x1D770` initializes the white and black context slots from the active palette's nearest-color indices, via `0x715E0`/`0xA3F54`. The selected-panel glyph blitter `0x1FF30` maps literal `1` to white and the established marker literals to black, leaving other literals unchanged. With the bound MAIN.PAL, white is index 145 and black is index 0. The tracked independent pixel probe applies this mapping and matches every byte in its tested 640×480 frames; it does not infer colors for unlisted glyph values.

That same draw function submits three bars for signed byte fields `+0x17`, `+0x19`, and `+0x1A`. The calls place them at `(116,415)`, `(116,435)`, and `(116,435)`, with height `6` and palette indices `0xE8`, `0xC4`, and `0xC8`. The bar helper at `0x2FF50` skips nonpositive values; otherwise its requested width is `max(1, 45*value/100)` for these calls. The source contains no upper clamp. The renderer draws those raw field rectangles in call order, so the third may cover part of the second at their shared row. These are field and drawing facts only; the field meanings and the coincident final two rows are not inferred here. The third field also gates an adjacent icon draw, which does not establish a user-facing label. The bar callsite, signed-width helper, rectangle routine and clipped framebuffer fill are pinned in `actor-panel-text-evidence.json`.
