# Selected actor portrait draw

The selected-actor details path calls the actor's virtual draw slot from two panel render methods. At `0x266EC` in function `0x265F0` and `0x2800D` in `0x27F20`, the actor pointer is in EAX, its vtable is in ECX, and the caller has loaded EBX=`0x2A`, EDX=`0x19` before `CALL [ECX+0x18]`. The actor vtable entry at `0x1121AC` resolves to `0x57050`.

`0x57050` sign-extends DX and BX, sets global `0x115B58` around the actor's virtual `+0x24` draw, then clears that global. In `0x57070`, DX supplies component X and BX supplies component Y. The selected panel portrait origin is therefore **(25, 42)** on the full 640×480 display. With `0x115B58` set, the draw path omits the world shadow call and does not subtract virtual-height/64 from the supplied Y. Its ordinary visibility, shade, and color path remains active.

Selection itself is connected: `0x2A450` resolves the chosen player-list entry to an actor record and passes it through `0x258E0` to the selected-panel object. The UI callsites above then draw the actor before the adjacent detail labels/statistics. The renderer helper takes the selected slot explicitly and adds this portrait over the already rendered indexed frame; it does not infer selection state or reconstruct the rest of the panel.

`actor_scene.rs` has an actual-resource test that compares the full portrait result against an independent component pixel walk, verifies the change stays in the left 128-pixel panel, and checks a synthetic clipped placement. The focused test passes. Exact source pins and the test command are recorded in [`actor-portrait-evidence.json`](../ghidra/actor-portrait-evidence.json).

## Adjacent details evidence

The top string in the `0x265F0` panel path uses the executable format string at `0x10D687`, whose bytes are `%s\n%s`. Its first argument is the pointer at actor-object offset `0xC0`; its second is loaded from `0x116090 + sign_extend(actor[0x16])*4`. The zeroed bytes in the initialized executable image are only the table's initial state. Startup function `0x1D770` fills the larger pointer array at `0x115E90 + 4*i` from the 604 parsed text strings (loop `0x1DA60`–`0x1DA7B`). Consequently `0x116090` is entry 128, and selector values 0–3 resolve entries 128–131. These are the four category strings used by this format path. The renderer can resolve them from the parsed text table without embedding their contents. The selector's wider domain is not established here, so a safe adapter should reject values outside the four admitted entries.

The first `%s` receives the actor-object pointer itself, but its bounded in-memory string layout and source of initialization have not yet been traced. This note therefore does not render or synthesize that first line. The format call passes the resulting text to context `0x187054` at draw origin `(0,0)`. Control handler `0x1FE70` dispatches newline byte `0x0A` to `0x1FEEC`, which advances the line accumulator by the height byte at the context's first glyph record and restores the saved baseline. This closes the newline mechanism, but not the first string's bounded source bytes.

That same draw function submits three bars for signed byte fields `+0x17`, `+0x19`, and `+0x1A`. The calls place them at `(116,415)`, `(116,435)`, and `(116,435)`, with height `6` and palette indices `0xE8`, `0xC4`, and `0xC8`. The bar helper at `0x2FF50` skips nonpositive values; otherwise its requested width is `max(1, 45*value/100)` for these calls. The source contains no upper clamp. These are field and drawing facts only; the field meanings and the coincident final two rows are not inferred here. The third field also gates an adjacent icon draw, which does not establish a user-facing label.
