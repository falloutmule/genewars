# Emulator automation assessment — 2026-10-13

Corroborated by primary documentation and read-only source inspection: these projects provide useful automation, but none establishes GeneWars input consumption or DOS4GW compatibility for this exact candidate. Keep them as optional evidence tools beside the Rust implementation. No emulator, original executable, installer or build ran for this assessment; no global configuration changed.

The smallest immediate capability experiment uses the existing pinned DOSBox-X executable's upstream debugger control protocol. The strongest candidate for bypassing host mouse injection is the separate pmanyeh native fork, but it needs a private build and a counter-focused empty probe. Its Python wrapper has no selected license and should not be copied into this project. rust-dos is a separate compatibility experiment, rather than a replacement for the verified environment.

## pmanyeh native bridge: useful, with concrete mouse restrictions

The bridge queues requests onto the emulator thread. Relative movement calls the internal mouse handler; button calls use the internal button handlers. Receipts contain a sequence and emulated dispatch time, with `guest_observed` explicitly unsupported. Guest render capture and final backend composite capture are different products; the latter includes scaling/filtering/letterboxing. Protected-mode debugger/watchpoint support is distinct from mouse-driver availability. [Agent guide](https://github.com/pmanyeh/DOSBox-X-MCP-Debugger/blob/c12b3e5a040bfcbf71666e19a0e82907799ab17c/AGENT_GUIDE.md).

Read-only inspection found important conditions in the actual native revision:

- `MouseMoveRelative` passes relative deltas directly to `Mouse_CursorMoved`. Its receipt is issued after the void handler returns, including cases where the handler performs no useful guest update.
- `Mouse_CursorMoved` returns early while the debugger is active. Run the guest during an input experiment; paused dispatch is not evidence of guest delivery.
- Mickey accumulation depends on `user_cursor_locked`. `capture.set` calls `GFX_CaptureMouse`, which changes SDL capture and `mouselocked`, but does not synchronize that variable. The ordinary SDL motion handler does. Thus programmatic capture plus internal relative motion can still produce no SI/DI counters. The driver also has a later host-position override depending on emulation mode.
- The newer absolute path temporarily forces/restores `user_cursor_locked` and adds normalized mickey deltas from its preceding absolute sample. Its first absolute sample contributes no delta. No reset of that sample on a mode change was found in this file; test transitions explicitly.
- Absolute availability requires real mode or v86 plus an established driver/video range. It is not a general protected-mode absolute interface. A DOS4GW program's switching between modes makes request-time availability relevant.
- Convenience `click_at` performs movement, press and release in one dispatch. An application sampling held/latch state can behave differently from separated press/release across emulated updates.

These are source-derived restrictions, not observed failures of this fork in GeneWars. [Native bridge dispatch and receipt implementation](https://github.com/pmanyeh/dosbox-x/blob/2042f26b9507631173579642a72523938eb7a407/src/debug/debug_ai.cpp), [mouse handler and availability gate](https://github.com/pmanyeh/dosbox-x/blob/2042f26b9507631173579642a72523938eb7a407/src/ints/mouse.cpp), [capture and SDL-motion synchronization](https://github.com/pmanyeh/dosbox-x/blob/2042f26b9507631173579642a72523938eb7a407/src/gui/sdlmain.cpp).

Build prerequisites: Visual Studio 2019 or later with desktop C++, the native `vs/dosbox-x.sln`, and a private x64 output. Its pinned config enables debugger and heavy debugger. The documented wrapper additionally needs Python and pinned MCP dependencies, but that wrapper is excluded by the license finding. An independently authored restricted newline-JSON client can use the public protocol without copying Python implementation. Loopback TCP is still an emulator control endpoint; restrict methods, serial calls, response size and host deadline. The native fork needs its own source/binary/config hashes and empty compatibility checks. The repository reports a redirected-console crash fix, while the guide retains console cautions: verify debugger operation under the chosen private launch arrangement rather than assuming our current redirected launcher is compatible. [Windows build instructions](https://github.com/pmanyeh/dosbox-x/blob/2042f26b9507631173579642a72523938eb7a407/README.development-in-Windows), [debug build config](https://github.com/pmanyeh/dosbox-x/blob/2042f26b9507631173579642a72523938eb7a407/vs/config.h).

## Upstream October 2026: two different interfaces

The official release notes really announce both an RPC debugger agent and MCP support. This does not mean the pmanyeh protocol became upstream, or that every distributed executable contains every agent feature. [Official release notes](https://dosbox-x.com/release-2026.10.01.html).

| Interface | Transport and enablement | Useful scope / limits |
|---|---|---|
| Upstream minimal debugger MCP | DOSBox-X connects outward to a host listener on `127.0.0.1`; `[dosbox] mcp_server=PORT`; serial text `REQ id PING/BREAK/EXEC` | Existing debugger commands; not the fork's JSON API. Resume acknowledgement is not a subsequent stopped-state observation. No direct mouse injection identified here. |
| Upstream structured RPC agent | Dedicated `Agent Debug SDL2` configuration; `C_DOSBOX_AGENT`; `--agent-config` private file; Windows named pipe | Structured debugging/session/register/memory/trace operations. No mouse/frame endpoint identified in the reviewed server. |
| pmanyeh native bridge | Native loopback TCP listener, documented default port9876; newline JSON | Internal input/captures/receipts in addition to debugging; separate build and protocol. |

The local verified package contains only Release and Release SDL2 directories. The existing Release SDL2 executable SHA-256 is `a82adcfa7af2784566cfeff74c077cefed08505396db2948b7e6aa7d4cee0832`. Static strings include `mcp_server`; that makes a minimal-MCP probe plausible, not already observed. Structured RPC availability is unestablished in that executable. Upstream configure defaults `--enable-dosbox_agent` off, and the VS project has separate Agent configurations defining it. `msbuild`, `cl` and `vswhere` were not found on this shell's PATH; this does not prove Visual Studio is absent. [Minimal protocol](https://github.com/joncampbell123/dosbox-x/blob/b6abbd5980a885f5f310a4088c59a8688d1b116c/README.debugger), [agent usage](https://github.com/joncampbell123/dosbox-x/blob/b6abbd5980a885f5f310a4088c59a8688d1b116c/docs/rpc-agent-usage.md), [agent build definitions](https://github.com/joncampbell123/dosbox-x/blob/b6abbd5980a885f5f310a4088c59a8688d1b116c/vs/dosbox-x.vcxproj), [configure defaults](https://github.com/joncampbell123/dosbox-x/blob/b6abbd5980a885f5f310a4088c59a8688d1b116c/configure.ac).

## rust-dos: credible separate DOS4GW candidate, untested here

The project documents a 386-family protected-mode/paging emulator, built-in DOS/DPMI and mouse support. It has a loopback HTTP debugger with relative mouse requests, screenshots, stop-at-entry, explicit wait/state sequence and protected-mode descriptor/page inspection. The debugging guide explicitly describes DOS/4GW clients using its default DPMI host. This supports feasibility, not GeneWars compatibility or equivalence to the existing DOSBox-X/DOS4GW path. Protected addresses need descriptor/page translation; a static Ghidra address is not automatically a valid physical breakpoint. [Pinned debugging guide](https://github.com/dividebysandwich/rust-dos/blob/9edb15c8ee8ae8349e152de03875dcc823d6137c/docs/llm-debugging.md).

Windows build instructions use Rust plus SDL2 development libraries, normally MSVC with SDL2.lib and its matching DLL. The project's README specifies SDL2 rather than SDL3 and documents the CI SDL2 version. Our local GNU Rust toolchain does not itself establish these prerequisites. Its default tests include network cases; the documented `cargo test-local` avoids those. If pursued, use a separate private checkout/toolchain/output and fresh copied fixtures. No source has been integrated and no compatibility test ran. [Build and feature documentation](https://github.com/dividebysandwich/rust-dos/blob/9edb15c8ee8ae8349e152de03875dcc823d6137c/README.md), [license](https://github.com/dividebysandwich/rust-dos/blob/9edb15c8ee8ae8349e152de03875dcc823d6137c/LICENSE).

## Smallest reproducible path forward

1. **No-build debugger capability check:** root supervises a fresh <=180s empty probe using the existing pinned DOSBox-X executable. Independent stdlib listener on a reserved loopback port starts first; a copied private config adds only `mcp_server`. Mount a new C containing only our authored timed logger/batch, retain secure mode, no game or disc. Serial requests: PING, BREAK, EXEC CPU and EXEC HELP; retain complete replies and confirm the stopped/running state independently before RUN. Unknown/unsupported commands or no connection terminate the experiment without a second emulator switch. This establishes remote-debugger availability only.
2. **Direct-input experiment after a separately pinned fork build:** same private empty logger bytes as probe012 (`MOUSE.COM`,1234bytes, SHA-256 `7e0f4eca31e358b25a5aad959ce9eeec3ecd7c7e876ac78bf28999bdc1ce5b3b`), fresh output, <=180s host watchdog. Keep the guest running. Compare capture query/set + relative `(32,0)`, `(0,16)`, `(-32,-16)` with absolute baseline then second point where allowed. Separate down/up across measured emulated intervals. Record receipts, guest clock/mode, guest frames, SI/DI and button events. Do not accept success from queued/dispatched alone. Use a separate authored mode-transition fixture before claiming the behavior survives text/graphics mode resets; record capture/relative-counter synchronization as a potential blocker, not silently patch it.
3. **Only after empty/protected-mode evidence:** a later root-owned original study could correlate the game's registered callback and software cursor with input and menu decisions. Resolve live selectors/base/paging first; use read-only observations, no original memory writes or patching. Keep exact candidate/media/config pins and the prior environment intact. No such original study is prepared or executed by this assessment.

Success has distinct levels: request accepted → internal handler dispatched → guest callback/counters changed → original consumer read the event → command/world state changed. Probe012 already established nonzero counters in its own real-mode logger; run006 did not establish the corresponding game stages. A screenshot with a host pointer or a transport receipt cannot bridge that gap. The menu's replay threshold is a separate logical-clock condition, not a reliable host-wall-time deadline for blind clicks.

Supporting metadata and private source hashes are in `emulator-automation-assessment.json`. This research adds no runtime dependency, MCP installation, source patch, launch script or new original execution.

## Subsequent observed empty capability test

Root subsequently executed the first capability experiment with an independently authored Python standard-library client and the unchanged pinned DOSBox-X executable. PING returned PONG. After BREAK was sent, the connection reset and the process returned 0xC0000409 before any CPU/HELP/RUN reply. The bounded session ended after 2.10 seconds; original game/disc files were not provided to the emulator, and the executable, original probe config and authored logger hashes remained unchanged.

This establishes the minimal control transport, but not debugger stop/resume or guest input control. Redirected-console handling and an early BIOS-stage break are possible explanations, not demonstrated causes. No second emulator or original game trial followed. Exact requests, process result, copied configuration and executed client snapshot are recorded in `mcp-capability-probe.json` and its private directory. This later execution is separate from the static assessment's original no-execution metadata.
