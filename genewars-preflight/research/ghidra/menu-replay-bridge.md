# Menu replay timer and mouse transition

`menu-replay-evidence.json` and `validate_menu_replay_bridge.py` pin the menu residence timer, replay module, DOS clock arithmetic and explicit mouse mode transitions. This is static evidence. It does not establish what host input succeeded or why run006 returned to the intro.

At the end of menu initialization, `0x7C7DB/E0` stores `0xA4F96`'s clock result in menu object+0x14. The shared tail of input handler `0x7C870` computes unsigned wrapped `(now-start)/100` and requests replay when the quotient exceeds30. The first triggering elapsed value is3100 centiseconds, or31.00 seconds. This clock is DOS INT21/AH2C time converted to hundredths through `0xBBA2A`, with `0xBBA90`'s baseline/midnight adjustment. Clock discontinuities remain a boundary.

The reviewed menu handlers do not refresh the timestamp on mouse movement or a press/release. This is a menu residence limit, not a proven input-reset inactivity timer. The check runs after action selection and can overwrite an earlier next-module request in the same call when already expired. A terminal process exit may not return to it. Input success near/after31 seconds therefore cannot be inferred from the subsequent intro.

Replay module `0x186F2C` is constructed from descriptor offset8 and vtable `0x112798`. Initialization `0x8DE50 → 0x7CB20 → 0x1BDB0` plays `intro/logo.smk`, `intro/biointro.smk`, then `intro/gw.smk` through `0x1BE50`, unless the playback-skip flag applies. Its next handler schedules menu `0x185008`, whose initialization resets the residence timestamp. This explains an automatic replay path without proving it was the path observed in run006.

For the normal successful mode path, the first two movies request mode1 with320×200 and reinitialize the software mouse with sensitivity1/1. When restore flag `0x118969 & 0x20` is set, each restores mode13 with640×480 and repeats that mouse initialization. The third movie uses the no-mode-switch path. Mode changes call `0xA33A8` to deactivate the mouse, then `0xA3164` reactivates it, sets its own bounds and centers its own cursor. The high-resolution center is therefore `(320,240)`. These are explicit branch assumptions, not measured run006 state.

The already-registered flag `0x19F354` survives teardown. Reinitialization skips DOS reset/function0C registration when it remains set, assuming the existing callback persists. Known zeroed buffers exclude the previous SI/DI words and division remainders. The driver’s counter/registration behavior across graphics modes is external; a same-mode empty logger result cannot settle it. Calling `0xA3164` while already active instead returns failure without resetting sensitivity or position.

Menu initialization selects cursor image record5 through `0x80130 → 0x7AD10`; that changes image/hotspot without another recenter or sensitivity setter. Foreground inhibition `0x19F350` is cleared by successful teardown/reinitialization and normal cursor-draw completion. The separate inhibition `0x19D220` has one direct writer in the reference graph: the command-line L/l switch sets it to1. The reviewed normal video/menu routines do not clear it. Indirect writes and actual runtime gate values remain outside this direct-reference claim.

Movement still requires an active mouse and movement event mask1. The callback uses SI/DI mickey counters; absolute CX/DX do not drive this software cursor. The preceding mouse receipt defines the immediate inhibition and deferred pending-delta behavior. Centered cursor artwork and working buttons do not independently establish which motion registers or gates the guest received.

A discriminating future reference check should timestamp the first labelled menu and finish calibrated captured relative motion, a visible cursor-position check and press/release within20 seconds, before the31-second transition. Preserve timing/capture evidence and stop if movement fails rather than repeat blind target clicks. An independent empty logger can first exercise the matching low/high graphics mode sequence to test callback/counter persistence. This tranche neither runs nor modifies the original program and does not assert that a root action succeeded.
